# schema-codegen-bridge

[![CI](https://github.com/standard-librarian/prisma-schema-codegen-bridge/actions/workflows/ci.yml/badge.svg)](https://github.com/standard-librarian/prisma-schema-codegen-bridge/actions/workflows/ci.yml)
[![License: MIT](https://img.shields.io/badge/license-MIT-blue.svg)](./LICENSE)

Define your data model **once**, as a ZenStack `.zmodel` schema, and derive
every downstream typed artifact a local-first, offline-capable app needs
from it: a **Jazz** CoValue schema, a **ts-rest** contract, and a
**BetterAuth** `additionalFields` config — all validated through the same
Effect Schema / Standard Schema bridge, all generated by real ZenStack v3
CLI plugins.

`zod-prisma` generates Zod from a Prisma schema. ZenStack generates an
access-policy-enforcing client from an extended schema. Both are the same
idea: **one schema, one generator, no drift.** This project extends that
idea the rest of the way through the local-first stack, instead of
hand-maintaining three parallel schemas that quietly fall out of sync.

## What's in here

| Package | What it generates |
|---|---|
| [`@codegen-bridge/generator-core`](./packages/generator-core) | Shared IR over the ZModel AST — every other package builds on this instead of re-walking the AST |
| [`@codegen-bridge/plugin-jazz-schema`](./packages/plugin-jazz-schema) | A Jazz CoValue schema (`co.map`/`co.list`) |
| [`@codegen-bridge/plugin-ts-rest-contract`](./packages/plugin-ts-rest-contract) | A ts-rest CRUD contract (Effect Schema via Standard Schema) per model marked `@@tsRestContract` |
| [`@codegen-bridge/plugin-betterauth-claims`](./packages/plugin-betterauth-claims) | A BetterAuth `additionalFields` config from your `@@auth` model's enum fields |
| [`schema-codegen-bridge`](./packages/cli) | A CLI wrapper (`schema-codegen-bridge generate`) around `zen generate` with schema validation |

Plus [`examples/pos-inventory-demo`](./examples/pos-inventory-demo): a real
schema exercising all three plugins together, with real `@@allow` access
policies and a [cross-artifact verification script](./examples/pos-inventory-demo/verify-shape.ts)
that checks the three generated outputs actually still agree with each
other.

## Quickstart

```bash
pnpm install
cd examples/pos-inventory-demo
npm run verify   # zen generate -> tsc -p . -> cross-artifact assertions
```

To use this in your own project, add the plugin packages you need as
dependencies, declare them in your `.zmodel`, and either run `zen generate`
directly or through this bridge's CLI (which validates the blocks are
present first):

```zmodel
plugin jazz {
    provider = '@codegen-bridge/plugin-jazz-schema'
    output = '../generated/jazz-schema.ts'
}

plugin tsRestContract {
    provider = '@codegen-bridge/plugin-ts-rest-contract'
    output = '../generated/ts-rest-contract.ts'
}

plugin betterauthClaims {
    provider = '@codegen-bridge/plugin-betterauth-claims'
    output = '../generated/betterauth-claims.ts'
}
```

```bash
npx schema-codegen-bridge generate
```

## Why a CLI wrapper, not just three plugin blocks

Each generator is a real ZenStack plugin — that wiring can't be hidden
behind a CLI, because ZenStack needs the `plugin {...}` blocks declared
directly in the consumer's `.zmodel` to register the custom attributes they
contribute (`@@tsRestContract`, and `@@auth`, which is core but still needs
the target model annotated in-schema). Copy-pasting those three blocks by
hand into every consumer project is exactly the kind of drift this whole
project exists to eliminate on the data-model side, so `schema-codegen-bridge`
at least makes the *generation step* consistent: one command, and a
specific, actionable error (with a copy-pasteable snippet) if a schema is
missing one of the three blocks, instead of a confusing failure discovered
later.

## Status

All of `PLAN.md`'s core milestones (M0–M6) are done. Every generated
artifact has been verified against a real installed dependency — not just
type-checked in isolation, but (where it matters) executed at runtime and,
for `verify-shape.ts`, deliberately broken once to confirm the check
actually catches drift. See:

- [`PLAN.md`](./PLAN.md) — milestones, scope, and open questions
- [`docs/plugin-api-notes.md`](./docs/plugin-api-notes.md) — the real
  ZenStack v3 / BetterAuth / ts-rest APIs this relies on, several of which
  differ from this project's own original guesses
- [`CHANGELOG.md`](./CHANGELOG.md) — what's new, and the known limitations
  that are tracked rather than hidden (most notably: `plugin-ts-rest-contract`
  currently requires `@ts-rest/core@3.53.0-rc.1`, since Standard Schema
  support isn't in a stable ts-rest release yet)

## Publishing

Packages aren't published to npm yet. Every publishable package
(`generator-core`, the three plugins, `cli`) has real metadata (`files`,
`exports`, `license`, `repository`, peer dependencies) and passes
`npm publish --dry-run` — verified in CI on every push. To actually publish:

```bash
npm login   # as whichever npm user/org should own the packages
pnpm run publish:dry-run   # sanity check first
cd packages/<package> && npm publish --access public   # repeat per package
```

The `@codegen-bridge` npm scope isn't reserved by anyone in particular —
whoever publishes first should either register that org or rename the
scope to their own first.
